# AP0 — M3 CLI Exit-Lattice Closure

Finding: `A22-001`

Priority: `P0 / HIGH`

Current state:

`m3_evidence_cli.execute()` now correctly runs the scoped Lean build and records subprocess return status. However `main()` returns `0` unconditionally after writing the receipt.

That means a receipt may correctly contain:

```text
lean_build.check_status = FAIL
stage_status = HELD_LEAN_BUILD_AND_SOURCE_INSTANCE
```

while the shell receives success.

## Required patch

Implement deterministic CLI exit semantics:

```text
0  authoritative required execution completed and admitted
1  required execution completed but failed
2  required execution could not be completed / execution error
```

At minimum:

- `lean_build.check_status == PASS` → `0`;
- `lean_build.check_status == FAIL` → `1`;
- `lean_build.check_status == ERROR` → `2`.

Static theorem-presence or parametric-tail PASS must never override the Lean execution exit class.

## Required tests

- fake `lake` return `0` → CLI exit `0`;
- fake `lake` return non-zero → CLI exit `1`;
- missing executable → CLI exit `2`;
- timeout/OSError → CLI exit `2`;
- receipt is still written with the matching internal status when output is requested.

Closure target: `PASS[M3_CLI_EXIT_STATUS_BOUND]`.

# AP1 — Hosted Authority Must Be Runtime-Derived

Finding: `A22-002`

Priority: `P0 / HIGH`

Current state:

`execute_build_request()` defaults `working_directory_class` to `HOSTED_CLEAN_CHECKOUT`. A local caller can therefore produce a canonical receipt that labels itself hosted even while the provenance envelope says `provider = LOCAL`.

This is an authority contradiction even when all file hashes are correct.

## Required patch

Do not allow a caller-controlled/default string to grant hosted authority.

Required model:

```text
local invocation
  -> ISOLATED_CLEAN_BUILD

GitHub Actions invocation with required hosted runtime identity
  -> HOSTED_CLEAN_CHECKOUT
```

`HOSTED_CLEAN_CHECKOUT` must be derived from execution context, not accepted merely as a function default or unconstrained CLI parameter.

Minimum hosted identity checks before granting hosted class:

- `GITHUB_ACTIONS == "true"`;
- non-empty workflow identity;
- non-empty run id;
- valid positive run attempt;
- expected runner platform class;
- provenance envelope bound to the canonical receipt digest.

The canonical receipt and provenance envelope must not contradict one another.

## Required tests

- local environment → receipt class cannot be `HOSTED_CLEAN_CHECKOUT`;
- forged partial GitHub variables → fail closed or remain local authority;
- complete simulated hosted environment → hosted class allowed;
- `provider=LOCAL` + `HOSTED_CLEAN_CHECKOUT` contradiction rejected;
- canonical receipt hash remains independent from run-specific provenance fields.

Closure target: `PASS[HOSTED_AUTHORITY_RUNTIME_DERIVED]`.

# AP2 — One Admission Path: Strict JSON → Schema → Runtime Semantics

Findings: `A22-003`, `A22-004`

Priority: `P0 / HIGH`

Current state:

Strict JSON parsing is implemented, but schema validation is not consistently part of runtime admission. CI currently checks that schemas themselves are valid schemas; it does not guarantee that every custody document is validated against its schema before semantic use.

This leaves two authority surfaces:

```text
JSON Schema
Python hand validator
```

with non-identical coverage.

Examples from current code:

- v3 top-level `additionalProperties: false` is stronger than `validate_manifest()`;
- source-binding and compiled-target closed shapes are schema-defined but not uniformly enforced by the runtime validator;
- compiled receipts contain authority fields such as `command_spec`, `build_cleanliness_class`, `dependency_surface_profile`, and `canonicalization_profile`, while `_compiled_receipt_matches()` validates only a narrower subset directly.

## Required patch

Create one project-owned schema admission layer, for example:

```text
load_strict_json
      ↓
resolve expected schema id
      ↓
Draft202012Validator.validate
      ↓
runtime semantic validation/evaluation
```

Required custody documents:

- M4 v3 manifest;
- Lean build request;
- compiled evidence receipt;
- execution provenance envelope when consumed;
- migration receipt;
- mutation corpus.

Unknown schema ids fail closed. Runtime semantics may be stricter than JSON Schema, but schema-defined prohibitions must never be bypassable through the normal CLI/API path.

## Required adversarial convergence tests

For every admitted document type, test at least:

- undeclared top-level field;
- undeclared nested field;
- missing required field;
- wrong enum/const;
- invalid relative path;
- malformed hash;
- correct schema but runtime-semantic failure.

Expected invariant:

```text
schema rejects
  => runtime admission rejects

schema admits + runtime semantic rule fails
  => runtime admission rejects
```

No test should require schema and runtime to be textually identical; the requirement is monotonic fail-closed admission.

Closure target: `PASS[SCHEMA_RUNTIME_ADMISSION_CONVERGED]`.

Finding: `A22-005`

Priority: `P1 / MEDIUM-HIGH`

Two parent-plan semantics are currently executed implicitly rather than represented explicitly in v3 data.

## AP3-A Support boundary policy

Current evaluator behavior implicitly allows touching intervals and gaps so long as ordering/inclusion passes. The parent plan required an explicit policy.

Add an explicit contract object, for example:

```json
"boundary_policy": {
  "allow_gaps": true,
  "allow_touching": true,
  "endpoint_convention": "CLOSED_CONTROL_INTERVALS"
}
```

The evaluator must execute the declared policy rather than relying on hidden Python behavior.

## AP3-B Cone dependency relation

Current threshold comparison hardcodes:

```text
node > each dependency
```

Represent that meaning explicitly, for example:

```json
"dependency_relation": "STRICTLY_GREATER_THAN_DEPENDENCIES"
```

Future source-derived obligations may use a different relation. Graph direction alone must not silently define mathematical meaning.

## Schema/runtime tests

- missing policy/relation in v3 → FAIL;
- unsupported enum → FAIL;
- declared touching allowed → PASS on touching fixture;
- touching disallowed → touching fixture FAIL;
- declared gap policy is executed;
- threshold order is checked under the declared relation.

Closure target: `PASS[EXPLICIT_SUPPORT_CONE_POLICY]`.

# AP5 — Exact Rational Resource Bound Is Per Component

Finding: `A22-007`

Priority: `P1 / MEDIUM`

Current `_fraction()` rejects strings longer than 513 characters. That approximates `256 + '/' + 256`, but it does not enforce the parent contract's actual rule of at most 256 digits per numerator and denominator.

A 300-digit numerator with a short denominator may remain below the total-length limit.

## Required patch

After strict lexical validation:

```text
numerator digits   <= 256
denominator digits <= 256
```

Sign is not counted as a digit. Integer-only values apply the numerator bound. Denominator remains strictly positive and non-zero.

Required tests:

- 256-digit integer → admitted if otherwise valid;
- 257-digit integer → FAIL;
- 256/256 digit rational → admitted if otherwise valid;
- 257-digit numerator → FAIL;
- 257-digit denominator → FAIL;
- negative numerator follows same magnitude-digit bound.

Closure target: `PASS[EXACT_COMPONENT_LIMITS_ENFORCED]`.

# AP6 — LIVE Dependency Surface Re-Verification

Finding: `A22-008`

Priority: `P1 / MEDIUM`

Current live producer regenerates dependency output and binds `dependency_surface_sha256` into the compiled receipt. The M4 verifier checks that this field has SHA-256 shape, but does not independently re-hash the generated dependency artifact during LIVE verification.

This leaves `.olean` bytes independently rechecked while dependency bytes are producer-bound only.

## Required patch

For LIVE evidence, make dependency-surface bytes independently verifiable.

Preferred v0.2.3 design:

- compiled target record carries a safe relative `dependency_surface_path`;
- receipt binds that path and its SHA-256;
- path is constrained under the declared evidence/dependency root;
- LIVE verifier re-reads the dependency artifact and compares its digest;
- replay mode verifies the recorded receipt only and does not imply current dependency-file presence.

If adding the field changes an already versioned public receipt contract incompatibly, introduce an additive compiled-evidence schema version rather than silently changing the meaning of the existing schema id.

Required tests:

- dependency file missing in LIVE → FAIL;
- dependency bytes drift → FAIL;
- traversal path → FAIL;
- replay without local dependency artifact remains valid under replay semantics;
- LF/CRLF and root normalization remain canonical under the declared profile.

Closure target: `PASS[LIVE_DEPENDENCY_BYTES_REVERIFIED]`.

## 8. Final boundary

> the v0.2.2 evidence-integrity implementation survived post-implementation scrutiny, the remaining false-green and authority-ambiguity surfaces were closed, and replay/live/source/receipt/dependency/mutation boundaries are executable rather than implied by prose.

output, execution context, and boundary are made inspectable, and the verifier
is required to fail when its declared scope is exceeded.
