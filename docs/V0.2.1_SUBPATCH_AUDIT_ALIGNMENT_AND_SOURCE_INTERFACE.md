This sub-patch is not a blanket downgrade of the repository. Several properties are already strong and must not regress while structural debt is repaired.

## Mathematical and formal-verification governance — Grade: `A-`

Verified strengths:

- explicit non-claims are encoded in module docstrings, receipts, and `non_claims` lists rather than left to README prose;
- `contracts.py::_validate_claim_gate()` rejects self-attested theorem `CONFIRMED` status even when a contract author writes favorable check labels;
- the Navier--Stokes contract preserves core theorem scope as executable schema/validation requirements, including:
  - `smooth_divergence_free_initial_data`;

  - `forced_navier_stokes`;

  - formulation `forced_clay_C_or_D`;
  - explicit non-claim `unforced_global_regular_or_blowup`;
  - BKM quantity `time_integral_vorticity_Linf`;
- static Lean presence is already accompanied by warnings that it is not build or semantic-equivalence evidence;
- bounded numerical diagnostics carry explicit `UNVERIFIED` or manufactured-control authority rather than theorem authority.

These properties form the repository's strongest governance layer. The sub-patch must preserve them while narrowing terminology elsewhere.

## System software engineering — Grade: `B+`

Verified strengths:

- deterministic receipt replay and byte-stability checks where byte identity is intentional;
- CRLF/LF canonicalization for the current textual source-hash path;
- path-traversal protection for receipt paths;
- exact rational arithmetic for selected custody controls;
- explicit dependency-cycle and dangling-dependency checks;

Residual debt lowering this grade:

## Compiler / Lean source interfacing — Grade: `C+`

The repository correctly invokes the real Lean/Lake toolchain in hosted CI, but source-meaning extraction remains text-oriented:

- declaration discovery by regex;
- signature truncation by string markers such as `:= by` and ` where`;
- ordered binder checks by substring search;
- no Lean-owned elaborated declaration metadata export is yet consumed by the verifier.

This is the largest architectural mismatch between terminology and mechanism. It should be repaired by a Lean-owned exporter, not by progressively larger Python regexes.

The code's internal authority boundaries are materially stronger than the first-screen README framing. The public description currently mixes present capability with future research lanes.

# 2B. External ecosystem corroboration and new constraints

A targeted review of Lean, GitHub, Hugging Face, DEV Community, and NeuralOperator discussions produced several implementation-relevant constraints. These sources do not replace direct repository evidence; they are used only where they clarify a design boundary already present in NSRW.

## Lean declaration export is already a real ecosystem pattern

The `leanprover/lean4export` project provides a Lean-owned declaration exporter that emits versioned NDJSON from Lean's elaborated environment rather than scraping source text. Its export metadata includes exporter version, Lean version, and Lean Git hash, and declaration records encode theorem/definition types and expression structure. The exporter can also target selected declarations.

References:

- `https://github.com/leanprover/lean4export`
- `https://github.com/leanprover/lean4export/blob/master/format_ndjson.md`
- `https://github.com/leanprover/lean4/blob/master/src/Lean/Environment.lean`

This materially strengthens SP2. The preferred path is no longer merely a hypothetical custom exporter. NSRW should first evaluate whether a pinned compatible `lean4export` revision can supply the required declaration/type/binder metadata for the pinned OpenAI toolchain. If not, build the smallest Lean-owned exporter necessary using the same `Environment` / `ConstantInfo` model.

New constraints:

- exporter identity is itself a pinned dependency;
- record exporter commit/version, Lean version/Git hash, export-format version, target declaration, and source commit;
- fail closed on exporter/toolchain incompatibility;
- do not parse pretty-printed theorem text when an exported `Expr`/declaration representation is available;
- canonical metadata should distinguish lexical source location from elaborated declaration identity.

A Lean ecosystem issue also documents real failure caused by using a `lean4export` binary from a mismatched Lean version. Therefore exporter/toolchain compatibility is part of evidence custody, not an installation detail.

Reference:

- `https://github.com/leanprover/comparator/issues/33`

## Hugging Face revision pinning should resolve once to an immutable commit

Hugging Face documentation explicitly supports dataset/model revision by commit SHA and documents a stronger pattern for multi-file acquisition: resolve a branch/tag once to an immutable commit and use that resolved revision for all files. This avoids two downloads made seconds apart observing different commits if a mutable branch changes.

References:

- `https://huggingface.co/docs/huggingface_hub/guides/manage-cache`
- `https://huggingface.co/docs/datasets/package_reference/loading_methods`

The current E2 source contract already requires `revision`, file identity, and SHA-256. Future admitted external artifacts should strengthen this to distinguish:

```text
requested_revision
  user-facing branch/tag/commit input

resolved_commit
  immutable Hub commit used for every acquired file

source_file_sha256
  exact admitted file bytes
```

For multi-file model/dataset acquisition, resolve once and use one snapshot/one resolved commit. A repository name or `main` alone is not custody.

A NeuralOperator issue reporting a Navier--Stokes dataset filename mismatch further reinforces that file identity must come from a pinned repository state and digest rather than an assumed filename convention.

Reference:

- `https://github.com/neuraloperator/neuraloperator/issues/708`

## Learned-model reproducibility requires numerical-backend policy, not seed alone

A 2026 NeuralOperator issue reports materially different PINO behavior across RTX 4090 / PyTorch 2.6 and RTX 5090 / PyTorch 2.8, traced by the reporter to tensor-core precision behavior and mitigated by disabling TF32 / requesting IEEE FP32 behavior.

Reference:

- `https://github.com/neuraloperator/neuraloperator/issues/720`

This does not affect current E2 because E2 contains no learned model. It does change the admission contract for future E3/E7 learned-model lanes. In addition to seed and package versions, receipts should record at minimum:

- GPU model / accelerator class;
- PyTorch/JAX version;
- CUDA version;
- cuDNN or equivalent backend version where applicable;
- TF32 / FP32 precision policy;
- deterministic-algorithm settings where applicable;
- dtype policy for model, inputs, residual evaluation, and FFTs;
- checkpoint digest.

A learned-model receipt must not use `same seed` as shorthand for `same numerical execution semantics`.

PhysicsNeMo documentation similarly treats deterministic data loading as an explicit opt-in tied to controlled RNG streams, reinforcing that stochastic reproducibility is a declared runtime property rather than an assumed default.

Reference:

- `https://github.com/NVIDIA/physicsnemo/blob/main/physicsnemo/datapipes/datapipes.md`

## Build provenance can be stronger than repository-local hashes

The parent M4 patch correctly states that repository-local hashes establish bounded consistency, not independent authenticity. GitHub now provides artifact attestations that cryptographically bind an artifact to workflow/repository/commit/build provenance using OIDC/Sigstore-backed attestations.

References:

- `https://docs.github.com/en/actions/concepts/security/artifact-attestations`
- `https://docs.github.com/en/actions/how-tos/secure-your-work/use-artifact-attestations/use-artifact-attestations`

This suggests an optional post-v0.2.1 hardening lane:

```text
canonical evidence receipt
      ↓ digest
hosted build artifact
      ↓
GitHub artifact attestation
```

The attestation must remain a provenance/authenticity layer, not mathematical authority. GitHub's own documentation explicitly notes that an attestation links an artifact to source/build context; it does not establish that the artifact is mathematically correct or secure.

DEV Community discussions on SLSA, SHA-pinned Actions, provenance, and signing broadly corroborate this direction, but they add no stronger normative requirement than the official GitHub provenance documentation and therefore are treated as secondary commentary only.

## External-review conclusion

The external research does not justify expanding NSRW into a CFD/SciML framework. It strengthens four existing design decisions:

1. replace Lean text scraping with Lean-owned exported declaration metadata;
2. pin external datasets/models to one resolved immutable revision and exact file bytes;
3. treat learned-model reproducibility as hardware/backend/precision custody, not seed custody alone;
4. keep integrity hashes separate from optional cryptographic build provenance.

## F-SP-001 — M3 build evidence can be fabricated by tool presence

Classification: `CONFIRMED_DEFECT`

Severity: `CRITICAL`

Current code in `src/nsrw/m3_evidence_cli.py` performs:

```text
lake = shutil.which("lake")
lean = shutil.which("lean")

check_status = PASS if lake and lean else ERROR
build_attempted = True
commands = ["lake build", "lake env lean NavierStokes.lean"]
```

No build subprocess is executed in `execute()`.

Therefore the current program can report:

```text
lean_build.check_status = PASS
build_attempted = True
```

when the only observed fact is that two executable names are resolvable on `PATH`.

This is not a cosmetic labeling issue. It violates the project rule `ABSTAIN > FABRICATE` because an execution event is asserted without execution evidence.

The existing test suite only tests the missing-toolchain branch. It does not test a fake executable returning non-zero, because the CLI never invokes the executable.

Required remediation is owned by this sub-patch, not the M4 parent patch.

## F-SP-002 — Lean source binding is textual inspection, not Lean semantic extraction

Classification: `CONFIRMED_DEFECT` for authority labeling; `VALID_LIMITATION` as a temporary locator mechanism.

Severity: `HIGH`

Three independent code paths use text-level source inspection:

1. `m4_audit.py::_normalized_declaration_signature()` uses `text.find(declaration)` and searches for textual terminators such as `:= by` and ` where`.
2. `m4_audit.py::_source_fragments_are_ordered()` uses ordered substring search.
3. `contracts.py::_verify_lean_item()` and `profile_closure.py::audit_lean_crosswalk()` use regular-expression declaration presence checks.

These checks are useful as pinned textual locators. They are not a Lean parser and do not bind to elaborated declaration semantics.

Important distinction:

```text
textual declaration presence
  !=
parsed Lean syntax
  !=
elaborated declaration type
  !=
paper--Lean semantic equivalence
```

The existing code is partially honest about this boundary: `profile_closure.py` labels its result `STATIC_FORMAL_SOURCE_LOCATOR_NOT_BUILD_PROOF`, and `contracts.py` warns that static presence does not establish build success or semantic equivalence.

The remaining problem is that M4 terms such as `source_quantifier_binding` and `quantifier custody` can read stronger than the implementation unless evidence classes are explicit.

## F-SP-004 — Current M4 mutation suite is a manifest-regression harness, not upstream semantic-drift evidence

Classification: `VALID_LIMITATION`

Severity: `HIGH` for public wording; `MEDIUM` for software correctness.

The current M4 mutation functions alter a deep-copied Python manifest in memory. Several target fixed list positions such as `obligations[0]` and `obligations[1]`.

The v2 baseline-delta algorithm is materially better than the earlier `any FAIL => killed` design:

```text
new_failures = mutated_failures - baseline_failures
kill = expected_detector in new_failures
```

The no-op contaminated-baseline regression test also proves that a pre-existing unrelated failure does not automatically kill a mutation.

Therefore the criticism that the current suite is completely tautological is too strong.

However, it still proves only:

> selected self-authored manifest corruptions are rejected by selected self-authored detectors.

It does not prove:

> arbitrary upstream Lean semantic drift will be detected.

The correct current evidence label is therefore closer to:

`MANIFEST_MUTATION_REGRESSION`

than to a generic semantic-drift detector.

The parent patch owns staged detector oracles, stable id/family targeting, and external JSON mutation fixtures. This sub-patch owns terminology and the future source-interface mutation lane.

## F-SP-006 — Numerical diagnostic kernels have real substance but lack stability/convergence receipts

Classification: `VALID_LIMITATION`

Severity: `MEDIUM`

### Scaling

`scaling.py` uses exact `Fraction` arithmetic for exponent algebra and correctly tests altered exponents. This is genuine mathematical computation and should remain classified as `EXACT_EXPONENT_ALGEBRA`.

No vectorization or CFD solver is required for this role.

### Differential operators

`operators.py` implements pointwise second-order central differences with default fixed step sizes. Tests use smooth linear/shear manufactured fields and verify small residuals, wrong-force detection, divergence detection, and invalid-step rejection.

What is not currently established:

- observed order under `h, h/2, h/4` refinement;
- cancellation sensitivity over multiple scales;
- tolerance selection from a convergence study;
- robustness on steep/high-frequency manufactured fields.

The audit's claim that catastrophic cancellation necessarily occurs is too strong without an executed step-sensitivity study. The correct finding is that the current evidence does not characterize that risk.

### Profile closure

`profile_closure.py` implements deterministic Simpson quadrature, explicit axis handling, one-sided endpoint derivatives, derived radial flux, and canonical pressure with explicit tail input. Tests cover the axis limit, endpoint derivatives, exact manufactured profiles, and invalid domains.

What is not currently established:

- quadrature-panel convergence;
- derivative-step sensitivity;
- coupled quadrature/difference error estimation;
- stability for oscillatory source-shaped controls.

These are appropriate next diagnostics. They are not reasons to rewrite the kernel as a CFD engine.

## F-SP-009 — ProofGraph traversal is correct at current scale but not indexed for growth

Classification: `VALID_LIMITATION`

Severity: `LOW` now / `MEDIUM` if the evidence graph becomes large.

`ProofGraph.outgoing()` and `incoming()` filter the full flat edge list on each query. `critical_path()` then recursively explores children without memoizing the longest path already computed for a shared descendant.

For the current small curated graph this is acceptable and the implementation is easy to inspect. However, in a highly convergent DAG, the same descendant subgraph can be recomputed once per distinct upstream path. The number of paths in a DAG can grow exponentially with node count, so the current recursive implementation does not have a stable large-graph complexity bound comparable to a standard dynamic-programming longest-path pass.

This is not a correctness defect in the present fixtures. It is scalability debt.

Recommended hardening:

- maintain adjacency indices for outgoing/incoming edges rather than scanning the flat list on every query;
- preserve deterministic edge ordering at serialization boundaries;
- after cycle validation, compute critical path with memoized DAG dynamic programming;
- add synthetic fan-in/fan-out graph benchmarks and output-equivalence tests against the current implementation;
- do not optimize away the explicit cycle guard merely for speed.

# 4. Sub-patch implementation tracks

## SP0 — M3 Evidence Execution Recovery

Priority: `P0 / CRITICAL`

Status target: `PASS[M3_EXECUTION_BOUND_RECEIPT]`

Required changes:

1. Replace PATH-presence attestation with actual `subprocess.run()` execution.
2. Record for each command:
   - command argv;
   - bounded working-directory class;
   - return code;
   - stdout digest;
   - stderr digest;
   - toolchain identity;
   - source commit;
   - target where applicable.
3. `build_attempted = True` only after process creation is actually attempted.
4. Missing executable -> `NOT_EXECUTED`/`ERROR`, never PASS.
5. Non-zero process exit -> FAIL/HELD.
6. Static declaration presence must never produce compiled-build authority.
7. CLI exit code must be non-zero on failed authoritative execution.
8. Historical M3 automated build receipts derived from PATH presence must be retained but marked `INVALIDATED` or `SUPERSEDED`.
9. Separately executed M3R evidence may survive only when it is re-issued as execution-bound evidence.

### SP0-A — Historical invalidation tombstone

Do not silently edit, replace, or delete previously published M3 receipts whose build authority depended on PATH-presence attestation.

Create a permanent tombstone document:

`docs/stage_receipts/M3_HISTORICAL_INVALIDATION.md`

The tombstone must record, for every affected historical receipt that can be identified:

```text
receipt_sha256
original_status
original_location_or_release
invalidated_assertion
invalidation_reason
finding_id = F-SP-001
discovery_date
superseding_receipt_sha256, if one exists
preserved_original_location
```

Required invalidation reason:

`F-SP-001: execution assertion without subprocess dispatch`

Rules:

- historical receipt bytes remain immutable;
- invalidation changes evidence authority, not historical existence;
- no old PASS is silently rewritten into a new status in place;
- release notes and canonical status output must point to the tombstone when affected evidence is referenced;
- if the complete historical receipt set cannot be reconstructed, state that incompleteness explicitly rather than inventing missing hashes.

This is claim-custody behavior: a discovered verifier defect revokes authority transparently while preserving the historical record.

Mandatory tests:

- fake `lake` on PATH returning exit `1` -> build FAIL;
- fake `lake` returning `0` but no target artifact -> build FAIL;

### SP4-D — Parent staged-oracle execution discipline

The parent M4 plan owns the staged mutation oracle. This sub-patch adds an implementation constraint intended to prevent test-matrix explosion and accidental authority mixing.

Use a sparse oracle matrix, not a Cartesian product of every mutation × every detector stage × every evidence mode.

```text
full_manifest
  schema / contract / hard-gate behavior
```

```text
test_mutation_against_full_manifest
test_mutation_against_isolated_evaluator
test_mutation_against_evidence_mode
```

- if full-manifest schema validation rejects an input, downstream full-gate evaluators are `NOT_REACHED`, not failed obligations;
- an isolated evaluator test may still be required for the same malformed value if the oracle declares it applicable;
- evidence-mode tests run only for mutations whose semantics depend on replay/live state;
- `allowed_secondary_detectors` remains explicit, but no stage is executed merely to populate the matrix.

This preserves staged-oracle meaning without turning the mutation bank into an unnecessary combinatorial CI burden.

## SP5 — Numerical Diagnostic Stability Receipts

Priority: `P2 / MEDIUM`

Status target: `PASS[DIAGNOSTIC_STABILITY_CHARACTERIZED]`

This track improves the evidence boundary without converting the project into a CFD solver.

### SP5-A — `operators.py`

Add a manufactured wide-band step-sweep utility rather than relying only on three monotonically shrinking points. The declared sweep should span both truncation-dominated and, where observable, roundoff-dominated regimes. A logarithmic family such as

```text
1e-1, 3e-2, 1e-2, 3e-3, 1e-3, ... , 1e-7
```

may be used after scaling it to the characteristic coordinate/time scale of the manufactured problem. The exact sweep is part of the receipt and must not be hidden in code defaults.

The expected error model depends on derivative order and must not be collapsed into one universal optimum-step formula.

For a second-order centered first derivative, the qualitative model is:

```text
E1(h) ≈ C_t h^2 + C_r eps_machine / h
```

which gives the familiar heuristic scale `h* ~ eps_machine^(1/3)` only up to problem-dependent constants and coordinate scaling.

For a second-order centered second derivative/Laplacian component, the qualitative model is:

```text
E2(h) ≈ C_t h^2 + C_r eps_machine / h^2
```

with heuristic scale `h* ~ eps_machine^(1/4)`, again only up to problem-dependent constants and scaling.

These asymptotic scales are diagnostics, not acceptance thresholds. The implementation must measure the actual manufactured-control error surface.

Record at minimum:

- operator kind and derivative order;
- floating-point format / machine epsilon used by the execution;
- characteristic scale used to interpret `h`;
- derivative/residual estimate at each step;
- absolute and relative error against a manufactured analytic target when available;
- observed local refinement order where meaningful;
- minimum-observed-error step;
- whether a roundoff turnover/U-curve was observed in the declared range;
- selected production diagnostic step and reason.

If no U-shaped turnover is observed in the declared sweep, record `NOT_OBSERVED_IN_DECLARED_RANGE`; do not infer one from theory alone.

Do not claim catastrophic cancellation unless the executed sweep demonstrates it.

### SP5-B — `profile_closure.py`

Add bounded sensitivity controls for:

- Simpson panel counts, e.g. `64/128/256/512`;
- eta derivative step refinement;
- pressure-balance derivative step refinement;
- at least one smoother control and one higher-frequency manufactured profile that remains inside the declared domain.

Receipt should distinguish:

```text
formula identity target
quadrature error proxy
finite-difference error proxy
combined observed error
```

### SP5-C — performance is secondary

Vectorization may be added later for experiment throughput, but NumPy/JAX/PyTorch vectorization is not required to establish correctness of these bounded controls.

No release claim may describe these modules as a general CFD engine.

# 7A. Adopted implementation guardrails from final pre-implementation review

The following recommendations are adopted after technical correction. Parent-plan-owned items remain parent responsibilities; this section exists to keep cross-plan implementation semantics explicit.

## 7A.1 Historical evidence revocation is additive, not destructive

Adopted as SP0-A. Historical M3 receipts remain immutable and are authority-revoked through a permanent tombstone ledger. Missing historical hashes must be reported as incomplete inventory, never reconstructed from memory or invented.

## 7A.2 Lean semantic export is tiered

Adopted with correction as SP2-B. v0.2.1 may retain only explicitly downgraded textual locators. Semantic declaration custody moves to a later Lean-owned export lane. A project-owned minimal exporter is preferred over modifying the audited upstream repository when `lean4export` is incompatible with the pinned toolchain.

## 7A.3 Parent strict-JSON implementation guardrail

The parent plan owns `strict_json.py`. Its standard-library implementation must not rely on default `json.loads()` behavior for adversarial inputs.

Required implementation semantics:

```text
raw bytes
  -> MAX_BYTES check
  -> UTF-8 decode under declared BOM policy
  -> string-aware lexical depth scan
  -> json.loads(...,
       object_pairs_hook = duplicate-key rejector,
       parse_constant = raising non-finite rejector)
  -> post-parse recursive resource accounting
  -> schema/runtime validation
```

A correct duplicate-key hook may use pair-order inspection, but `parse_constant=None` is not sufficient: Python's default decoder admits `NaN`, `Infinity`, and `-Infinity`. The callback must raise on all such constants.

Depth pre-scan must be string/escape aware. Counting `{`, `}`, `[`, `]` with regex or raw byte counts is not an admissible depth check because those characters may occur inside JSON strings.

Post-parse accounting must enforce the parent contract's object-member, array-length, total-node, and related bounded-resource limits. Exact numeric resource bounds remain governed by the parent P2/P3 contracts.

## 7A.4 Parent staged mutation oracle is sparse and short-circuiting

Adopted as SP4-D. Full-manifest, isolated-evaluator, and evidence-mode tests are separate execution surfaces. Schema-first failure is authoritative for the full-manifest path; it does not require downstream evaluators to execute. Only semantically applicable stages and modes are tested for each mutation.

## 7A.5 Numerical step selection is operator-order aware

Adopted with correction as SP5-A. `eps^(1/3)` is a first-derivative heuristic, not a universal NSRW step rule. First- and second-derivative operators use different roundoff models, and empirical wide-band sweeps determine the observed stability region. U-curve absence in the tested interval is reported rather than inferred.

## 7A.6 Cross-plan consistency review completed

The bounded review was completed before v0.2.2 implementation. Its decision is:

```text
Parent P0-P5  <->  Sub-Patch SP0-SP8
  no duplicated or contradictory authority

release blockers  <->  roadmap gates
  no accidental dependency cycle

Definition of Done
  no mutually impossible requirements
```

No contradictory authority remains after the release/roadmap split in section
0A. Implementation is authorized only for that release-critical scope. Hosted
CI and release promotion remain separate gates.

# 8. Final boundary

Successful completion of this sub-patch would mean:

> the public description, execution receipts, source interface, mutation terminology, numerical-diagnostic evidence, CI ownership, and graph status vocabulary match the authority of the code that actually exists.

It would not mean:

> a new Navier--Stokes theorem has been proved, the OpenAI proof has been independently verified in full, a selected noncomputable witness has been numerically reconstructed, or the project has become a CFD/SciML framework.

The governing principle remains:

> the core computation is not the claim of novelty. The contribution is the custody: isolating the exact checkable surface, reproducing it under a pinned environment, and making its boundary inspectable.

A strong audit harness is not one that uses stronger terminology. It is one whose terminology never outruns its evidence.
